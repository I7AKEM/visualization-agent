# Security, operations, deployment, and implementation delivery

## 1. Frozen implementation decisions

These choices remove implementation-time ambiguity:

1. Upgrade once, before feature work, from Pydantic AI 2.35.3 to exactly 2.36.0. Pin Pydantic, Pydantic Evals, Logfire, FastAPI, and transitive locks in the same compatibility PR. If the compatibility suite fails, stop; do not mix APIs from both versions.
2. Interactive turns/streaming use ordinary FastAPI processes with Postgres-authoritative command/state/outbox persistence. They do not keep a workflow process open while waiting for a human.
3. DBOS is the background durability/queue implementation for profile, analysis, export, scheduled refresh, and cleanup. Workflows use stable names/IDs and JSON-native versioned inputs; I/O is isolated in idempotent steps. Real-time UI events come from the transactional outbox, not buffered workflow event replay.
4. Release-1 common charts use GPT-Vis plus a G2 fallback/advanced adapter. Flint is not on the release-1 critical path; evaluate it after the stable artifact contract exists.
5. Pydantic Graph is not used for the top-level command state machine; explicit application state tables/transitions are simpler and durable. It MAY be used later inside a bounded workflow only through an ADR.
6. The production runtime is OCI containers on managed Kubernetes in the owner-approved data region, with managed Postgres, managed Redis, S3-compatible object storage, private container registry, secret manager, WAF/ingress, and an OpenTelemetry Collector. Local development uses Docker Compose equivalents.
7. The API has no permission to execute shell/code or access arbitrary file paths. Analysis/export workers have separate service accounts and network policies.
8. Prompt, model route, skill/context, renderer, semantic model, boundary, dataset, evaluator, and artifact schemas are versioned release inputs.

The organization must supply before production: chosen cloud/account/region, identity provider, data retention classes, approved model providers/routes, Mapbox account/token policy, authoritative Saudi boundary source/license, on-call owners, and business traffic/SLO confirmation. Engineers cannot invent these governance facts.

## 2. Threat model and controls

### 2.1 Assets

- uploaded and governed data, derived results, artifacts/exports;
- identity/session/delegation/connector/provider credentials;
- metric/semantic definitions and audit history;
- model prompts, skill/context packages, provider usage/cost;
- source code, images, deployment and telemetry systems;
- tenant isolation and service availability.

### 2.2 Adversaries/failure actors

- unauthenticated internet user;
- authenticated user exceeding workspace authority;
- malicious tenant/data uploader;
- compromised browser/session/service credential;
- malicious prompt content, external MCP server, community skill/package, or model output;
- dependency/supply-chain compromise;
- operator mistake;
- provider/worker/network/storage failure and resource exhaustion.

### 2.3 Mandatory controls

Identity/session:

- OIDC Authorization Code + PKCE; short-lived server session; secure/HTTP-only/SameSite cookies;
- CSRF protection for mutations, strict origin/CORS, session rotation at login/privilege change;
- MFA and conditional access inherited from IdP where policy requires;
- service identities use workload identity/mTLS, never user API keys in the browser;
- delegated external-agent token has audience, tenant/workspace/user, scopes, expiry, command limits, and non-forwardable policy.

Authorization:

- centralized policy function receives server identity + resource + action + context;
- default deny, field/row rules, classification/egress, publication/export policy;
- checked at ingress, job start, data read, cache, event delivery, result finalization, publish/export;
- policy version recorded with each decision and run.

Network:

- WAF/rate/request limits at ingress; TLS 1.2+;
- namespaces/service accounts/network policies separate web, API, analysis, export, data, telemetry;
- analysis worker egress denied; connector-specific worker uses domain/IP allowlist and proxy;
- export worker egress denied except reviewed asset proxy;
- database/cache/object endpoints private; metadata/link-local/private SSRF blocked;
- MCP uses TLS/auth and explicit server allowlist; stdio only in trusted local development.

Data:

- envelope encryption at rest, TLS in transit, secret manager/KMS, key rotation;
- immutable tenant-prefixed object keys generated by server; signed URLs shortest practical expiry;
- scan uploads, force download content disposition, never execute macros/formulas/active content;
- PII classification/minimization, retention/deletion legal hold, backup encryption;
- confidential/restricted rows do not enter external prompts or telemetry by default.

Application/model:

- strict schemas, allowlisted operations/components/tools, no arbitrary code;
- server-owned history/state; all user/data/skill/MCP/model content untrusted;
- bounded model/tool/context/token/cost budgets and circuit breakers;
- deferred approval is user-control only, not authorization; server reauthorizes tool/action;
- provider/model fallback cannot weaken policy, residency, modality, or quality.

Supply chain:

- protected branches, signed commits/tags according to organization policy, mandatory review/CODEOWNERS;
- lockfiles, hash-verified builds, minimal non-root images, read-only filesystem where possible;
- SBOM, provenance/attestation, Trivy/OSV/pip-audit/npm audit/license/secret scans;
- Renovate/Dependabot PRs run all affected contract/render/eval gates; no floating production tags;
- AntV/community skills pinned and reviewed as untrusted context, not executable authority.

## 3. Privacy and telemetry policy

Default production telemetry content:

- allowed: IDs (hashed/pseudonymous where possible), versions, mode/kind/status/error, counts/sizes, durations, budgets, model/provider route, tokens/cost, sanitized tool names, evaluation labels;
- denied: auth headers/cookies/tokens, connector strings, raw files/rows, full prompts/responses, unrestricted tool args/results, signed URLs, secrets, precise restricted coordinates;
- conditional: schema/column names, redacted examples, plan filters, narrative—allowed only by data classification and explicit secure-debug flag with expiry/audit.

`trace_include_content` is false in production by default. Redaction tests contain canary secrets/PII and fail release if they reach captured spans/logs/events.

Production/nonproduction use separate Logfire projects/tokens and retention/access policies. Trace sharing/export is a data disclosure and requires authorization.

## 4. OpenTelemetry trace contract

Required root/child spans:

```text
http.command
  authn
  authz
  command.validate
  command.idempotency
  intent.resolve
    agent.run? / model.request?
  clarification.create_or_resume?
  artifact.create
  outbox.commit
  stream.delivery

job.profile | job.analysis | job.export
  job.authorize
  object.read
  plan.compile?
  query.policy?
  execution
  result.validate
  object.write
  artifact.finalize
  outbox.commit
```

Required low-cardinality attributes:

- service/version/environment/release/region;
- request/command/run/artifact kind and status—not raw UUID as metric label;
- mode/data mode/model mode/resolved model route/prompt and skill versions;
- tenant tier/data classification, never tenant name as a metric dimension;
- retry/fallback/clarification/revision kind;
- row/byte buckets, renderer, error class;
- evaluator/dataset version and outcome.

Trace correlation IDs exist in Postgres audit and safe client errors. Raw IDs may exist in traces for lookup but not high-cardinality metric labels.

## 5. Service-level objectives

Initial objectives for the controlled beta; Phase 0 load measurements may tighten, but correctness/security gates cannot be relaxed.

| SLI | Objective/window |
|---|---|
| authenticated API availability excluding valid 4xx | 99.9% monthly |
| command acceptance p95/p99 | ≤300 ms / ≤800 ms |
| first status p95 | ≤500 ms |
| exact render first shell p95 | ≤1.5 s after accepted command |
| exact render first useful rows p95, small fixture | ≤2.5 s |
| analysis first shell p95 | ≤2 s |
| small golden analysis final p95/p99 | ≤15 s / ≤30 s |
| SSE reconnect to converged state p95 | ≤3 s |
| cancellation acknowledged p95 | ≤1 s; worker termination ≤5 s |
| finalized renderer success | ≥99.9% |
| accepted background job eventual completion | ≥99.5% excluding user/data-policy failures |
| exactness/numerical/tenant/security critical failure | zero tolerated; immediate incident |
| trace correlation completeness for accepted commands | ≥99.9%; 100% for errors/canary |

Capacity limits are product configuration, returned to UI and tested. Default beta limits until measured: 250 MiB upload, 5 million rows, 200 columns, 20 dashboard widgets, 10 concurrent commands/user, 50/workspace, 120-second analysis deadline, 180-second export deadline. Raising a limit requires performance/security evidence.

Recovery objectives:

- Postgres/object metadata RPO ≤5 minutes, RTO ≤60 minutes;
- no RPO claim for uncommitted in-flight events; committed outbox/state must survive;
- Redis loss RPO = irrelevant to authoritative state; service degrades/rebuilds;
- restore drill quarterly and before general availability.

## 6. Dashboards and alerts

Dashboards:

1. product/quality: success/failure, mode mix, exact/analysis, clarification/correction/undo, eval by target/language/model/release;
2. agent/model: request/tool counts, invalid output/repair, fallback, tokens/cost, latency, prompt/skill version;
3. data/workers: ingest/query/export duration, rows/bytes, queue lag, budgets, validation failures, cleanup;
4. streaming/render: first shell/data/final, disconnect/replay/gaps, renderer errors by version/browser;
5. security/privacy: authz denies, injection/policy blocks, cross-tenant canaries, redaction/evaluator status;
6. platform: availability/error, CPU/memory/disk, pods/restarts, DB/cache/object/collector/dependency saturation;
7. release: candidate versus baseline and rollback gates.

Alerts have severity, owner, threshold/window, user impact, dedupe, and runbook:

| Alert | Trigger | Severity/action |
|---|---|---|
| tenant/exactness/unsupported-numeric violation | any confirmed event | SEV-0: stop affected traffic, revoke publication, incident |
| secret/PII telemetry canary | any | SEV-0: stop export/telemetry path, rotate if needed |
| availability error-budget fast burn | 14.4× burn 1h/5m | SEV-1 page |
| slow burn | 2× burn 6h/30m | SEV-2 ticket/page by policy |
| quality critical online eval failure | any confirmed; evaluator healthy | SEV-1, disable model/prompt/release |
| p95 latency ≥2× SLO | 15 min | SEV-2 |
| queue lag > job SLO | 10 min | SEV-2 |
| provider/MCP/render failure spike | ≥5% 10 min and baseline delta | SEV-2; circuit/route |
| cost per success ≥2× baseline | 1h minimum volume | SEV-2; disable route/inspect |
| telemetry/evaluator gap | <99% expected 10 min | SEV-1 for blind errors, else SEV-2 |
| DB/object/worker saturation | predicted exhaustion <30 min | SEV-1/2 by impact |

## 7. Incident and kill-switch policy

Kill switches are server-side, audited, reversible, and independently target:

- model/provider/route/prompt/skill version;
- logical agent/tool/MCP server;
- analysis/export workers or connector;
- renderer/artifact kind;
- uploads/publication/sharing/export;
- tenant/workspace/release cohort;
- online evaluation/content capture.

Incident steps:

1. acknowledge and establish incident commander/severity/scope;
2. contain using smallest kill switch/rollback, prioritize data/security correctness;
3. preserve sanitized evidence and immutable audit;
4. verify recovery with original SLI and synthetic canary;
5. notify stakeholders under policy;
6. root-cause across application/model/tool/data/infrastructure;
7. add regression test/eval before corrective release;
8. postmortem with owners/dates and runbook/alert changes.

Required runbooks before beta: provider outage, DB/cache/object outage, stuck queue, stream replay gap, incorrect number, cross-tenant suspicion, sensitive telemetry, prompt/tool compromise, Mapbox outage/token abuse, failed migration, rollback, backup restore, cost spike, mass cancellation, data deletion request.

## 8. Environments and configuration

Environments: local, CI, development, staging, production. No shared databases, object buckets, Redis, secrets, model/Gateway keys, Mapbox tokens, or Logfire projects across staging/production.

Configuration:

- Pydantic Settings validates at startup; missing/unknown/unsafe values fail readiness;
- nonsecret config versioned; secrets by reference from secret manager;
- flags have owner, purpose, default, creation/expiry, environments, and removal ticket;
- production model catalog is server-signed/versioned; UI cannot add endpoints;
- all workers advertise supported contract/operation/renderer versions at readiness.

Health:

- liveness: process/event loop alive only;
- readiness: migrations compatible, Postgres/outbox available, required object store and policy/config loaded; optional provider failure does not kill readiness if circuit can refuse/fallback safely;
- startup warms no tenant data and performs no public rendering call;
- graceful shutdown rejects new commands, drains streams/outbox within deadline, releases leases, and leaves background jobs resumable.

## 9. CI/CD and release pipeline

```text
PR
→ static/type/schema + unit/property/contract/component
→ critical integration/E2E/security/eval
→ review/CODEOWNERS
→ merge immutable commit
→ reproducible build + SBOM/sign/scan
→ deploy staging
→ migrate expand phase
→ smoke/full eval/load-required subset/redaction/trace verification
→ production dark deploy
→ internal 1%
→ 5% canary
→ 25%
→ 50%
→ 100%
→ contract migration only after old version drained
```

Each canary step has a minimum volume/time and compares quality, critical failures, error, p95/p99, cost, fallback, renderer, and evaluator health. Any SEV-0/1 or scorecard breach automatically stops promotion and triggers the documented rollback/kill switch.

Database/schema changes use expand → dual-compatible deploy → backfill with checksums → switch readers/writers → contract in later release. Active DBOS workflow input schemas only receive backward-compatible optional fields; incompatible changes create a versioned workflow name and drain old runs.

Rollback order:

1. disable affected flag/model/prompt/skill/tool/renderer route;
2. route traffic to previous immutable deployment;
3. stop incompatible new jobs, leave old workers for old workflows;
4. reverse data migration only when explicitly proven safe; otherwise roll code forward with compatibility;
5. verify synthetic canary, error/quality/latency, and state/hash integrity.

## 11. Isolated task and integration protocol

Each `WP-00` through `WP-14` is implemented in a separate Codex task with a fresh context and separate Git worktree. Product feedback, approvals, and follow-up discussion stay in that task. Tasks may read this complete normative package but must not rely on chat history from another task.

Dispatch order is fixed:

| Wave | Tasks allowed to run | Entry condition |
|---|---|---|
| 0 | `WP-00` | specification merged or present in the task starting state |
| 1 | `WP-01` | WP-00 is accepted or conditionally accepted for owner-independent scaffolding, and the WP-01 owner/reviewer are assigned |
| 2 | `WP-02`, initial `WP-13` telemetry scaffolding | WP-01 exact locks and CI artifact available |
| 3 | `WP-03`, eval-corpus scaffolding owned by `WP-06` | WP-02 contract artifact/version published |
| 4 | `WP-04`, provider-independent portion of `WP-06` | WP-03 state/policy artifact published; provider work additionally requires provider approval |
| 5 | `WP-05`, provider-approved remainder of `WP-06` | WP-04 has green integration evidence; provider work additionally requires provider approval |
| 6 | `WP-07` | WP-04 and WP-06 have green integration evidence |
| 7 | `WP-08` | WP-05 and WP-07 have green integration evidence |
| 8 | `WP-09`, `WP-11` | their listed dependencies and owner inputs are green; missing map/semantic input disables that task's dependent feature |
| 9 | `WP-10` | WP-03, WP-05, WP-06, WP-07, WP-08, and WP-09 have green integration evidence |
| 10 | `WP-12`, completion of `WP-13` | all renderer/revision paths required by the task are integrated |
| 11 | `WP-14` | all work-package evidence packets are green |

The integration owner maintains one integration branch and is the only actor that merges work-package branches. Every task delivers:

- a commit hash and changed-path list;
- a requirement-to-test/eval evidence fragment;
- migrations and compatibility statement;
- runtime configuration and secret-name changes without secret values;
- observed tests with exact commands/results;
- risks, disabled features, and rollback instructions.

The integration owner must merge in dependency order, rerun the receiving branch's full required gates after every merge, and reject a task that changes another package's frozen contract without an approved contract-version change. Shared generated artifacts are produced by their owning package only: `WP-02` owns schemas/clients, `WP-06` owns the offline eval corpus, `WP-08` owns the renderer registry, and `WP-13` owns telemetry dashboards/runbooks. No task edits the same generated artifact by hand.

A dependent task is created only when its entry condition is met. This prevents an idle task from guessing missing contracts and ensures comments in one task cannot silently redefine another task's behavior.

## 12. Definition of done for every change

- normative requirement/issue linked;
- contract, migration, compatibility, and rollback addressed;
- tests written at the lowest effective layer and failure case included;
- relevant agent eval added/updated for model-driven behavior;
- no real provider call in unit/PR tests unless the eval job explicitly allows it;
- telemetry span/metric/error and redaction classification implemented;
- security/tenant/idempotency/budget/cancellation reviewed;
- Arabic/English, RTL/accessibility, calendar/geo considered where affected;
- documentation/runbook/limits/version manifest updated;
- CI passes on the exact built artifact; reviewer verifies behavior, not only code style.
